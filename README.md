# Домашнє завдання до теми 5 — Алгоритми пошуку

**Мета:** порівняти швидкодію трьох алгоритмів пошуку підрядка — Боєра–Мура (Boyer–Moore), Кнута–Морріса–Пратта (KMP) і Рабіна–Карпа (Rabin–Karp) — на двох статтях із курсу.

## Структура репозиторію

```text
goit-algo-hw-05/
├── main.py                 # Усі три реалізації, перевірки та benchmark
├── README.md               # Методика, результати й висновки
└── articles/
    ├── article_1.txt       # Стаття №1
    └── article_2.txt       # Стаття №2
```

- [Стаття 2: Методи та структури даних для реалізації бази даних рекомендаційної системи соціальної мережі](https://drive.google.com/file/d/1o5uZ8NBMtZmThGIeilCRWgspIOfOnbzQ/view)

Вихідні файли були в кодуванні Windows-1251. Копії у цьому репозиторії перекодовано у UTF-8 **без зміни текстових символів**. `main.py` підтримує обидва кодування. Дані розміщено локально, щоб вимірювання можна було повторювати без інтернету.

## Реалізовані алгоритми

| Алгоритм | Принцип | Асимптотична складність пошуку |
|---|---|---|
| **Бойєр–Мур** | Порівняння справа наліво, зсуви за поганим символом і хорошим суфіксом | Часто ефективний на практиці завдяки пропускам; найгірший випадок залежить від варіанта реалізації |
| **Кнут–Морріс–Пратт** | Таблиця найдовших власних префіксів-суфіксів (LPS) | **O(n + m)** у найгіршому випадку |
| **Рабін–Карп** | Ковзний поліноміальний хеш і перевірка збігів для уникнення хибних результатів | Очікувано **O(n + m)**, найгірше **O(nm)** через колізії |

Тут `n` — довжина тексту, `m` — довжина підрядка. Кожна функція повертає індекс першого збігу або `-1` за відсутності; для порожнього підрядка повертає `0`.

## Як запустити

Потрібен **Python 3.10+**. Сторонні бібліотеки не потрібні.

З кореневої директорії репозиторію:

```bash
python3 main.py
```

Додаткові параметри (доступні для повторення експерименту):

```bash
# Перевірити реалізації пошуку на граничних та випадкових прикладах
python3 main.py --self-test

# Змінити кількість викликів і повторів timeit
python3 main.py --number 20 --repeat 7

# Використати власні текстові файли (UTF-8 або Windows-1251)
python3 main.py --article-1 /path/article_1.txt --article-2 /path/article_2.txt
```

Програма виводить Markdown-звіт у консоль. Для відтворення таблиці не потрібні додаткові файли результатів.

## Методика експерименту

1. Зчитали два оригінальні тексти й підготували для кожного **наявний** підрядок довжиною 28 символів, перший збіг якого розташований у другій половині статті.
2. Створили **відсутній** підрядок тієї ж довжини, замінивши останній символ на `⟐`, якого немає у тексті. Відсутність перевірено програмно.
3. Для кожної пари «текст–підрядок» перевірили, що всі алгоритми повертають той самий результат, що й `str.find()`.
4. Виміряли час через `timeit.repeat(number=20, repeat=7)`. У таблиці використано **медіану семи вимірювань, поділену на 20**, у мілісекундах на один виклик.
5. Завантаження й декодування статей **не** входить у час. Підготовка таблиць/хешів всередині алгоритму **входить**. Це порівняння *готового пошуку з одним новим шаблоном*, а не багаторазового пошуку із заздалегідь підготовленим шаблоном.

Тестове середовище: **Python 3.13.5, Linux x86_64**. Час вимірювання не є константою: значення можуть змінюватися при повторних запусках залежно від обладнання та навантаження.

## Висновки

1. **Стаття 1:** в обох сценаріях найменший час показав **Boyer–Moore**; середній час становив близько **0.127 мс** за пошук.
2. **Стаття 2:** в обох сценаріях переміг **Boyer–Moore**; середній час становив близько **0.212 мс** за пошук.
3. **Загалом:** Boyer–Moore був найшвидшим у всіх чотирьох тестах. На обраних текстах і підрядках він обганяв KMP і Rabin–Karp, насамперед завдяки великим зсувам при невдалих порівняннях.
4. **KMP** гарантує лінійну складність `O(n + m)` навіть на несприятливих текстах. Його передбачуваність може бути важливішою за швидкість на окремому тесті.
5. **Rabin–Karp** тут виявився найповільнішим, але хешування може бути корисним у задачах зі спільною обробкою багатьох шаблонів або інших сценаріях пошуку.
6. **Обмеження:** чотири вимірювані сценарії та конкретні Python-реалізації не доводять універсальної переваги Boyer–Moore. Результат залежить від структури текстів, довжини шаблонів, застосованих евристик, інтерпретатора, процесора та системного навантаження. Навіть одноразовий пошук і повторні пошуки з попередньою обробкою шаблону можуть мати різних переможців.

**Висновок:** для розглянутих двох статей найбільш ефективним був **Boyer–Moore**, але вибір алгоритму в практичних системах потрібно підтверджувати вимірюваннями на реальному навантаженні.
